How it works

Private content. Checkable history.

This local research demo separates a record's encrypted content from the factors needed to open it. Here is what it does, and what it does not promise.

A small, understandable workflow

  • Simple create, append, and history workflow
  • Opaque identifiers rather than names
  • Immutable event and fragment objects
  • Parent links forming an auditable history
  • Local operation after setup; no cross-device sync yet

Health-specific protections

  • Both factors required to enroll, append, and read records
  • Authenticated encryption for stored record content
  • Clinician signatures and patient authorization MACs
  • FHIR resources rather than generic descriptions
  • No public history URL or demographic patient search

Small by design

This interface uses plain HTML, CSS, and JavaScript, with no GUI framework. The record service depends on a small BlobStore interface, not a cloud provider. Memory and local-file adapters implement the same read, create, and compare-and-swap operations.

Where the demonstration runs

The browser saves synthetic factors and a clinician private key in local storage, which is not a secure production key store. Both are sent to the loopback server for record operations. That service decrypts and verifies records, and returns the timeline to this browser; decryption is not browser-only. The local-file store persists encrypted content on this computer.

What is not implemented

Real biometric matching, recovery, clinician revocation, cross-clinic authorization, distributed storage, and offline synchronization remain future work. The object store can observe opaque access patterns and some capsule metadata. The demo makes no clinical, regulatory, or production-readiness claim.

A stored synthetic factor proves neither physical patient presence nor informed consent. Verified provenance does not establish clinical truth. Hiding the timeline removes rendered content; it is not a guarantee of secure memory erasure.
